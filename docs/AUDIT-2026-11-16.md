## Critical

### C1 🔬 Edits from a device whose clock is behind are silently lost, and devices then disagree
`worker/index.js:611`. A general table keeps a change only `WHERE excluded.at > records.at`, and `at` is the device's own
clock. The server clamps clocks that run *ahead* (`:742`) but not clocks that run *behind*.
**Probe:** an expense saved at *now*, then edited from a device whose clock is one hour slow, comes back as
`applied: 0, refused: 0`. The cloud keeps the old amount (1000, not 5000). The device is not told, so it keeps
showing 5000. The server row's `seq` does not move, so the device never re-downloads the cloud's copy. **The
two copies stay different for good.** The same happens to a refund or a sale edit from a till whose clock is behind.
The field-merge tables (products, customers, suppliers, batches) lose the field the same way.

**Fix**
1. Server: when the stored row is newer than the incoming change, count it as `stale` and return those keys in the
   reply (as `refusedKeys`). The client then re-downloads those records, so the device at least converges.
2. Client (`src/sync.js`, and the Flutter sync): work out a clock offset from the reply's `Date` header, or a
   `serverTime` field, and stamp `updatedAt` with `Date.now() + offset`. Warn on the till when the clock is more than
   2 minutes off.
3. Long term: a hybrid logical clock (`max(local, lastSeen) + 1`) for `updatedAt`.
4. Test: the probe above as a v-suite, with "the device ends with the cloud's value" as the assertion.

### C2 🔬 A cashier can move or re-attribute any sale without `sales.edit`
`worker/policy.js:63-75`. `moneyView()` decides whether a sale "changed". It leaves out `date`, `cashier`, `number`,
`createdBy` and the shift.
**Probe:** a cashier token re-pushed an existing sale with `date: 2025-01-01` and `cashier: "Someone Else"`. The
cloud **accepted it** (`applied: 1`). A sale can be moved out of today's cash-up or into another person's shift, or
renumbered, and the money still "matches". Closed days are protected (`dayCloses`); open days are not.

**Fix.** Add `date`, `number`, `cashier`, `createdBy`, `shiftId` and `branchId` (already there) to the "identity" the
`unchanged` and `isRefundOnly` checks compare. Allow only `status`, `refundedAt` and `refundedBy` to change on the
refund path. Add a unit test in `tests/unit-policy.mjs`.

### C3 🔬 A cashier can change stock with fake "Sale" movements
`worker/policy.js:43,107-111`. Anyone with `pos.sell` may write a movement of type `Sale`. Its sign, size and sale are
never checked.
**Probe:** a cashier pushed `{type: 'Sale', qty: +500}` with no sale behind it. It was **accepted**. Stock is the sum of
movements, so 500 units appeared. A negative one makes stock disappear: theft cover, with no sale and no anomaly
recorded.

**Fix.** On the server, a `Sale` movement must:
- have `qty < 0`;
- carry a `saleId` that exists, or arrives in the same push;
- belong to a product on that sale's lines, with the quantities adding up.

A `Refund` movement must be positive and reference a sale marked refunded. If a check fails, refuse the movement, or
store it and raise an anomaly (the offline-first choice, as in step 3). Movements on the closed-day path already have
this shape.

## High

### H1 🔬 Changing or resetting a password does not sign out old sessions
`worker/index.js:229-235, 297-305`. A token is valid for 30 days. Only deleting or disabling the person ends it.
**Probe:** after the owner set a new password for the cashier, the old token still returned 200. A lost or stolen phone,
or a fired employee's browser, stays signed in after "change the password", which is the step people take first.

**Fix.** This needs no refresh-token work (step 10): add `pwAt` (or `tokenVersion`) to the user record. Set it in
`hashNew` and `resetPassword`, in `resetWithGoogle`, and on owner and admin password sets. Put it in the token as
`pv`. `authenticate()` already reads the user record, so refuse a token when `p.pv !== rec.pwAt`. Add a
"Sign out everywhere" button that just bumps it.

### H2 🔬 The patient calendar link: any staff member can get it, and it can never be revoked
`worker/index.js:1487-1490, 1709`. `/api/calendar-link` has **no permission check**. A cashier got it in the probe. The
feed (`:1504-1508`) lists **patient names, refill dates and their medications**: health data. The signature is a fixed
HMAC of the pharmacy id. The only way to end a leaked or ex-employee's link is to change `TOKEN_SECRET`, which signs
every device out.

**Fix.** Copy the daily-stock-sheet design (`:1699-1708`): a random key in `tenants.secrets`, rotatable by
`settings.manage`. Require `settings.manage` (or a new `calendar.share`) to see it. Add an option to show initials
instead of names. Also: fold ICS lines at 75 octets (RFC 5545), and validate `e.time` as `HH:MM` before putting it in
`DTSTART` (`:1530`).

### H3 🔬 Shared attachments can be overwritten by any colleague
`worker/index.js:1335-1338`. Uploads are `INSERT OR REPLACE` keyed by an id the client picks, with no owner check.
**Probe:** an admin uploaded `rx.pdf`. A cashier uploaded different bytes with the same id, and the admin's signed link
now serves **the cashier's file**. A prescription photo or an invoice in the chat can be swapped after the fact.

Also in this function:
- `chunks ≤ 40 × 800 KB` allows about 32 MB, above the 15 MB limit, and the sizes are never added up.
- Unfinished uploads are never cleaned up.
- No pharmacy has a storage quota.

**Fix.** Generate the id on the server at chunk 0, or refuse when `files`/`file_chunks` already has that id from another
`by_uid`. Refuse further chunks once the file is complete. Check the running size total. Add a daily job that removes
chunks with no `files` row after 24 h, and a per-pharmacy byte quota.

### H4 Every staff role can download all the books
`worker/index.js:583-587, 859-863`, and the same rules in `snapshot.js` and `window.js`. A full download hides only
payroll and sale checks. A cashier's token receives every expense, bank transaction, loan, supplier price, cost price
and every customer's details. The UI hides the Finance pages, but the data is on the device and in the API reply.

**Fix.** Extend `viewOf` with a per-table read rule that mirrors `TABLE_RULES`. For example, `expenses`, `bankTx`,
`loans` and `banks` need `finance`. The snapshot cache key already varies by view (`key`), so add the new flags
there. At minimum, strip `cost` from products for roles without `reports` or `inventory.edit`.

### H6 App updates are trusted on HTTPS alone
`electron/updater.cjs:104-109` and `src/update.js:56`. The SHA-256 values come from the same `version.json` on the same
host as the files. Anyone who can publish to the Cloudflare Pages project can push code to **every Windows and Android
till**, which then runs it with the offline database and sign-ins. That could be a leaked API token, a compromised CI
action, or a Cloudflare account takeover.

**Fix.** Sign `version.json` in CI with an Ed25519 key held only as a GitHub secret, in a protected environment that
requires approval. Embed the public key in the shell. Refuse unsigned manifests. Raise `SHELL` once to ship the
verifier.

## Low / hygiene

- `/api/errors` adds 1 to `devices` on every report, so it is really a second count (`worker/index.js:1673`). Store a
  device-id set or hash and count distinct values. The route also runs a pruning `DELETE` on every call, with no rate limit.
- The ICS feed adds up **every movement of the pharmacy** on each calendar refresh (`:1510`). Use the cached balances
  (`stockindex` / `window.js`) instead.
- `moveToTurso` copies `tenants` without the `branding` column (`:1295`). It is a one-off tool, but a re-run would drop logos.
- The pharmacy logo accepts `image/svg+xml` (`:1148`). It is safe inside `<img>`, but check that it is never used through
  `innerHTML` or in PDF generation. Consider raster only, as for attachments.
- The Electron `will-navigate` handler allows any `file:` URL (`electron/main.cjs:62`). Limit it to the app's own
  `dist` / update folders, as `protocol.handle` already does.
- The Hub buffers request bodies up to 50 MB in memory (`server/hub.mjs:111`) and serves plain HTTP on the LAN. The
  sync key and tokens cross the network in clear text. Document a Caddy front-end as the default, or issue a
  self-signed certificate on first start.
- `MAINTENANCE.md` names a personal mailbox for the Brevo account. Use a role address (e.g. ops@) so the account isn't tied to one person.
- `typecheck` covers 2 files. Widen `checkJs` to `worker/policy.js`, `worker/index.js` `sync()`, `src/money.js`,
  `src/sync.js` (REVIEW §3; still open).
- `worker/index.js` is 1,742 lines (135 KB), with every route in one `if` chain. Splitting it into route modules (REVIEW §3,
  step 17) is still not done. Most of the findings above sit in it.
